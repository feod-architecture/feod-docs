# Редакторский style guide FEOD

Этот документ фиксирует тон, язык и правила подачи для пользовательской документации FEOD. Его задача - сделать страницы единообразными по стилю, не смешивая объясняющий материал, практические guides и нормативный reference.

## Статус документа

- Документ нормативный.
- Все авторы страниц FEOD следуют этим правилам.
- Если локальная страница спорит с этим guide, корректируется страница.

## Цель стиля

Документация FEOD должна звучать как инженерная документация:

- точно;
- коротко;
- последовательно;
- без разговорной расплывчатости;
- без маркетингового тона.

Читатель должен быстро понять:

- что означает термин;
- какое правило действует;
- почему правило существует;
- как не нарушить его на практике.

## Базовые принципы

### Писать по одному смыслу за раз

- Один абзац раскрывает одну мысль.
- Одна страница отвечает на один главный вопрос.
- Если для ответа нужны и объяснение идеи, и пошаговый сценарий, и строгая норма, материал делится на несколько страниц.

### Давать короткие определения

- Определения пишутся в 1-3 предложениях.
- Первое предложение отвечает на вопрос `что это`.
- Второе и третье предложения, если нужны, отвечают на вопрос `зачем это нужно`.

### Объяснять спорные правила

- Если правило может показаться произвольным, после него обязателен раздел `Почему`.
- `Почему` объясняет инженерный мотив: контроль зависимостей, локализация изменений, предсказуемость структуры, снижение связанности, упрощение навигации.
- Формулировка `так принято` не считается объяснением.

### Показывать нарушение запрета

- Каждый запрет сопровождается примером нарушения.
- Недостаточно написать `не делайте так`; нужно показать, что именно считается нарушением.
- Для читателя должно быть ясно, где проходит граница правила.

## Тон по типам страниц

### Concept pages

- Тон объясняющий, но сдержанный.
- Цель - убрать неоднозначность термина или принципа.
- Допустимы короткие пояснения контекста, если без них определение читается неверно.

Пишите:

- `Модуль - это ...`
- `Этот принцип нужен, чтобы ...`

Не пишите:

- `Давайте разберёмся, что вообще тут имеется в виду`
- `На самом деле всё довольно просто`

Почему: такие вводные занимают место, но не добавляют смысла.

### Guide pages

- Тон практический и прямой.
- Guides могут быть чуть разговорнее reference, но не теряют точность.
- Допустимы формулировки, помогающие вести читателя по сценарию: `начните с`, `проверьте`, `если это не так, сначала исправьте`.

Пишите:

- `Начните с границ модуля, а не со списка файлов.`
- `Если зависимость не укладывается в public API, пересоберите контракт.`

Не пишите:

- `Можете попробовать сделать так`
- `Обычно тут как-нибудь справляются`

Почему: guide ведёт к результату, а не предлагает набор необязательных идей.

### Reference pages

- Тон нормативный.
- Приоритет у формулировок `должно`, `не должно`, `разрешено`, `запрещено`.
- Reference не уговаривает и не обсуждает настроение команды.

Пишите:

- `Уровень pages не импортируется в modules.`
- `Public API модуля должен быть явным.`

Не пишите:

- `Лучше не импортировать pages в modules`
- `Желательно держать public API явным`

Почему: reference нужен для проверки нормы, а не для интерпретации намерения автора.

## Язык и словарь

### Термины

- Используйте только термины, закреплённые в [terminology.md](./terminology.md).
- Для верхних уровней используйте `app`, `pages`, `modules`, `common`, `global`.
- Основной русский термин - `уровень`.
- `Слой` допустим только как пояснение для аудитории FSD и не должен становиться основным словом страницы.

### Public API

- На одной странице выберите одну форму: `public API` или `публичный API`.
- Не смешивайте формы без причины.
- Не используйте разговорные варианты вроде `паблик API`.

### FEOD-сущность

- Не называйте FEOD-сущность вариантом DDD entity.
- Если страница затрагивает DDD, различие надо проговорить явно.

## Стиль формулировок

### Предпочтительные конструкции

Используйте:

- `это`
- `нужно`
- `должно`
- `не должно`
- `разрешено`
- `запрещено`
- `используйте`
- `проверьте`
- `исключение`

Избегайте:

- `кажется`
- `наверное`
- `в целом`
- `как будто`
- `по сути`
- `довольно`
- `просто`
- `очевидно`

Почему: такие слова размывают норму или маскируют отсутствие точного объяснения.

### Длина фраз

- Базовая единица - короткое утверждение.
- Сложную мысль лучше разбить на два предложения, чем упаковать в одно длинное.
- Если правило нельзя быстро прочитать вслух без потери смысла, его надо упростить.

### Пассивный залог

- Предпочитайте активные формулировки.
- Вместо `может быть использовано` пишите `используйте` или `разрешено использовать`.

Почему: активная конструкция короче и лучше показывает норму.

## Структура абзацев и списков

### Абзацы

- 2-4 предложения на абзац достаточно для большинства страниц.
- Длинные плотные блоки текста разбивайте.
- Первый абзац страницы или раздела должен давать суть, а не разгон.

### Списки

- Используйте списки, когда читатель должен быстро сравнить условия, ошибки, критерии или варианты.
- Не превращайте всё в списки: определение и правило часто лучше читаются как короткий абзац.
- В checklist каждый пункт должен проверяться ответом `да/нет`.

### Таблицы

- Таблицы используйте только для сопоставления ролей, уровней, разрешений, ограничений и матриц.
- Если таблица не помогает принять решение быстрее, замените её списком.

## Примеры

### Good example

- Показывает норму в естественном контексте.
- Должен быть минимальным, но не игрушечным.
- Читатель должен понимать, что именно в примере считается правильным.

### Bad example

- Показывает конкретное нарушение текущего правила.
- Под плохим примером обязательно подпишите нарушение одной короткой фразой.
- Не используйте карикатурные примеры, которые никто бы не написал в реальном проекте.

Почему: пример полезен только тогда, когда читатель узнаёт в нём реальную рабочую ситуацию.

## Запрещённые приёмы

### AI-пометки

Запрещено:

- упоминать, что текст написан ИИ;
- добавлять дисклеймеры про модель, генерацию или ассистента;
- маркировать разделы как `AI note`, `generated`, `LLM tip`.

Нарушение:

```md
> Этот раздел был сгенерирован автоматически и может требовать уточнения.
```

Почему: пользовательская документация должна говорить от лица проекта, а не от лица инструмента.

### Внутренние шутки и снисходительный тон

Запрещено:

- добавлять мемы, подмигивания, шутки для команды;
- писать в тоне `ну тут всё понятно`;
- высмеивать типовые ошибки читателя.

Нарушение:

```md
Не складывайте всё в common, если не хотите потом страдать всем отделом.
```

Почему: шутка быстро стареет и делает нормативный текст менее точным.

### Псевдоуверенность без нормы

Запрещено:

- выдавать предпочтение за правило без явной маркировки;
- использовать смягчители вместо точной нормы в reference.

Нарушение:

```md
Обычно modules стараются не зависеть от pages.
```

Почему: читатель не понимает, это запрет, рекомендация или случайная привычка автора.

### Привязка к VitePress-реализации

Запрещено:

- описывать страницу через обязательные компоненты VitePress;
- встраивать в шаблоны требования к фронтматтеру, сайдбарным ключам или теме;
- путать редакторскую структуру с техническим устройством сайта.

Нарушение:

```md
Каждая reference-страница должна использовать конкретный VitePress-компонент для матрицы правил.
```

Почему: шаблоны FEOD должны переживать смену движка и не зависеть от реализации документационного сайта.

## Правила для спорных мест

Если автор формулирует правило, которое может вызвать вопрос `почему именно так`, он обязан:

1. Сформулировать норму коротко.
2. Добавить объяснение `Почему`.
3. Показать корректный пример.
4. Показать нарушение.
5. Указать исключения или явно написать, что исключений нет.

Если любой из этих пунктов пропущен, страница считается недоработанной.

## Самопроверка автора

Перед публикацией страницы проверьте:

1. Страница использует один из утверждённых шаблонов из [page-templates.md](./page-templates.md).
2. Определения короткие и отвечают на вопрос `что это`.
3. Все спорные правила объяснены через `Почему`.
4. Каждый запрет сопровождается примером нарушения.
5. Тон страницы соответствует её типу: concept, guide или reference.
6. Страница не зависит от VitePress-специфики.
7. Термины согласованы с [terminology.md](./terminology.md).

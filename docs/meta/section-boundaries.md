# Границы Tools, Blog и About

Статус: нормативный

Этот документ фиксирует, какие материалы относятся к `Tools`, `Blog` и `About`, а какие должны оставаться в `Docs`, `Guides` или `Reference`.

## Главное правило

`Tools`, `Blog` и `About` не заменяют документацию методологии.

- `Tools` объясняет сценарии применения инструментов вокруг FEOD.
- `Blog` хранит статьи, мнения и истории, но не правила.
- `About` объясняет мотивацию, сравнения и развитие FEOD.
- Нормативные правила живут в `Docs`, прежде всего в `Reference`.

## Tools

`Tools` - вторичный раздел относительно методологии. Он показывает, как инструменты помогают применять FEOD, но не делает инструмент главным способом понять FEOD.

В первом этапе допустимы подтверждённые направления и артефакты:

- `FEOD Analyzer`;
- `ESLint plugin`;
- `AI rules`;
- `FEOD config`.

Для каждого направления нужно описывать:

1. Когда инструмент нужен.
2. Какой сценарий он поддерживает.
3. Какой артефакт получает команда.
4. Какие ограничения у инструмента есть сейчас.
5. Где заканчивается автоматическая проверка и начинается архитектурное ревью.

Нельзя:

- обещать готовую техническую реализацию без подтверждённого артефакта;
- писать о будущей возможности как о существующем продукте;
- заменять методологическое правило ссылкой на инструмент;
- выносить в `Tools` базовые правила импортов, public API или уровней.

## Blog

`Blog` - место для контекста, историй и мнений. Он может помогать понять подход, но не является источником правил.

В `Blog` подходят:

- история появления FEOD;
- migration stories;
- разбор архитектурных ошибок;
- спорные вопросы и trade-offs;
- сравнение подходов в формате статьи;
- заметки о развитии tooling.

В `Blog` не должны жить:

- матрица импортов;
- правила public API;
- структура уровней `app`, `pages`, `modules`, `common`, `global`;
- glossary и определения терминов;
- правила именования;
- code smells как нормативный список.

Если статья содержит правило, оно должно быть продублировано или вынесено в `Reference`. В статье можно ссылаться на правило, но нельзя делать статью единственным источником нормы.

## About

`About` объясняет, зачем существует FEOD, с чем его сравнивать и куда методология развивается.

В `About` относятся:

- мотивация;
- сравнение с FSD;
- сравнение с NestJS-модулями;
- сравнение с Atomic Design;
- roadmap;
- позиционирование FEOD как framework-agnostic методологии для frontend-приложений.

`About` не должен мешать первому обучающему пути. Новичок должен понять FEOD через `Обзор`, `Быстрый старт` и базовые материалы, а не через длинную историю мотивации.

## Материалы бывшего раздела `Прочее`

| Старый материал | Новое место | Решение |
| --- | --- | --- |
| FAQ | `Get Started / FAQ` | Переписать как короткие ответы на частые вопросы. |
| `FEOD - это очередной FSD?` | `FAQ` + `About / Сравнение с FSD` | Короткий ответ оставить в FAQ, подробное сравнение вынести в About. |
| `Где хранить...?` | `Guides / Где хранить код` + `Reference` | Практический decision tree - в Guides; строгие правила размещения - в Reference. |
| `Глоссарий` | `Reference / Glossary` | Переписать после фиксации терминологии. |
| `Roadmap` | `About / Roadmap` | Описывать развитие методологии, не смешивая с базовыми правилами. |

## Проверка перед публикацией

Перед добавлением страницы автор проверяет:

1. Если страница содержит правило, ей место в `Reference`, `Structure` или `Core Concepts`, а не в `Blog`.
2. Если страница обещает инструмент, она явно показывает текущий статус и ограничения.
3. Если страница объясняет мотивацию или сравнение, она не прерывает onboarding.
4. Если материал пришёл из старого `Прочее`, для него указано новое место из таблицы выше.

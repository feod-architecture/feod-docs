# Продуктовые решения

Статус: нормативный

Этот документ фиксирует продуктовые решения для первого этапа документации FEOD. Его задача - закрыть открытые вопросы из PRD так, чтобы дальнейшая авторская работа не зависела от неоднозначностей области действия.

## Область действия

Решения ниже обязательны для:

- терминологии;
- информационной архитектуры;
- раздела Tools;
- раздела About;
- планирования следующих авторских материалов.

Техническая реализация сайта, VitePress и любые framework-specific implementation details в область действия этого документа не входят.

## Принципы решений

- Сначала фиксируем одну понятную и непротиворечивую версию FEOD.
- Документация не обещает того, что ещё не существует как продукт или артефакт.
- Методология первична, инструменты вторичны.
- Первый этап должен уменьшать неоднозначность, а не покрывать все возможные варианты.

## Решения

### 1. Каноническое имя верхнего уровня: `global`

#### Решение

Каноническое имя верхнего уровня - `global`. В основной терминологии, примерах структуры и reference-материалах используется только `global`.

Совместимость с `globals` допускается только как исторический или миграционный контекст. Это не альтернативная норма и не второй равноправный вариант FEOD.

#### Rationale

- PRD уже фиксирует `global` как стабильный термин и имя папки.
- Одновременная норма `global` и `globals` создаёт лишнюю вариативность в базовом обучающем пути.
- Для первого этапа важнее единообразие терминов, чем поддержка нескольких написаний на равных правах.

#### Downstream impact

- **Terminology:** использовать только `global` как нормативный термин.
- **IA:** migration- и FAQ-материалы могут объяснять переход с `globals`, но не должны представлять его как каноническое именование.
- **Tools:** любые правила, проверки и AI-guidance должны считать `global` базовой нормой.
- **About:** FEOD описывается как методология со стабильными именами уровней; `globals` упоминается только как legacy-вариант, если вообще нужен.

### 2. Одна каноническая версия FEOD на первом этапе

#### Решение

На первом этапе документируется одна каноническая версия FEOD. Отдельные вариации, профили или альтернативные интерпретации FEOD не входят в первичную область документации.

#### Rationale

- PRD требует единых терминов, непротиворечивых правил импортов и ясного базового пути обучения.
- Несколько равноправных вариаций увеличивают когнитивную нагрузку и блокируют написание core-страниц, reference и guides.
- До появления устойчивых кейсов лучше закрепить один канон, а не каталог вариантов.

#### Downstream impact

- **Terminology:** все ключевые определения пишутся в единственном нормативном варианте.
- **IA:** страницы уровня Overview, Quick Start, Core Concepts, Structure и Reference строятся вокруг одного канона.
- **Tools:** инструменты описываются как поддержка канонической FEOD, а не как система переключаемых профилей.
- **About:** FEOD позиционируется как одна методология с фиксированным базовым ядром, а не как семейство несовместимых вариантов.

### 3. Tools: фиксируем только реально существующие направления, остальное - roadmap

#### Решение

На первом этапе раздел Tools сохраняется, но остаётся вторичным по отношению к методологии. В документации можно описывать только следующие tool-направления, уже закреплённые в PRD как минимальные страницы:

- ESLint plugin;
- AI rules;
- FEOD config.

Для каждого такого направления разрешено документировать только реальный сценарий применения и продуктовую роль. Нельзя обещать готовность, глубину интеграции или технические свойства, которые ещё не подтверждены отдельным артефактом.

Всё, что не относится к этим трём направлениям или не имеет подтверждённого текущего артефакта, маркируется как roadmap либо остаётся вне области первого этапа.

#### Rationale

- PRD прямо запрещает обещать инструмент без объяснённого реального сценария.
- PRD также прямо говорит, что техническая реализация инструментов на этом этапе вне области работ.
- Для контентного этапа достаточно определить продуктовые категории Tools, не превращая их в ложные обещания о зрелости.

#### Downstream impact

- **Terminology:** использовать формулировки уровня "tooling-направление", "сценарий применения", "roadmap", а не язык готового продукта без оснований.
- **IA:** в Tools допускаются только страницы про ESLint plugin, AI rules и FEOD config; прочие идеи не поднимаются в основную навигацию как существующие инструменты.
- **Tools:** каждая страница должна явно разделять "что это за направление" и "что уже доступно сейчас". Если текущая доступность не подтверждена, это roadmap.
- **About:** FEOD не позиционируется как набор зрелых инструментов; основа продукта - методология, а tooling является поддерживающим слоем.

### 4. Позиционирование FEOD: шире, чем frontend-фреймворк, но не шире, чем frontend-приложение

#### Решение

FEOD на первом этапе позиционируется как методология архитектуры для frontend-приложений. Она не привязана к конкретному UI-фреймворку, но и не описывается как универсальная архитектура для любых типов программных систем.

Иными словами:

- FEOD не ограничен React, Vue, Nuxt, Next или Svelte;
- FEOD не следует продвигать как общесистемную или backend-first методологию;
- базовый объект документации - frontend application и его кодовая база.

#### Rationale

- PRD прямо запрещает делать FEOD зависимым от конкретного фреймворка.
- В то же время вся предложенная IA, примеры, guides и структура уровней ориентированы именно на frontend application architecture.
- Расширение позиционирования "вообще для всего" размазывает термины и создаёт неподтверждённые ожидания.

#### Downstream impact

- **Terminology:** использовать формулировки "frontend-приложение", "клиентский код", "UI-приложение", когда это нужно для точности.
- **IA:** Overview, Quick Start, Examples и migration guides должны опираться на frontend-сценарии.
- **Tools:** tooling описывается как поддержка FEOD в frontend codebase.
- **About:** FEOD подаётся как framework-agnostic frontend methodology, а не как универсальная архитектурная теория для любого домена.

### 5. Английская версия не входит в первый этап

#### Решение

Английская версия документации не входит в область первого этапа. Источник истины для первой версии - русскоязычная документация.

#### Rationale

- Первый этап уже включает большую контентную нормализацию и закрытие смысловых неоднозначностей.
- Параллельная двуязычная разработка увеличивает редакторскую стоимость и риск расхождения терминов до стабилизации канона.
- Сначала нужно закрепить терминологию и структуру на одном языке, затем масштабировать.

#### Downstream impact

- **Terminology:** русский текст является первичным носителем нормативных формулировок.
- **IA:** не требуется дублировать навигацию, URL-политику или контентные блоки под два языка на первом этапе.
- **Tools:** не требуется обещать двуязычные tool-pages и описания.
- **About:** можно кратко указать, что English version возможна позже, но она не является обязательством первой поставки.

### 6. Отдельные версии под React/Vue/Nuxt/Next/Svelte не нужны на первом этапе

#### Решение

Отдельные версии документации под React, Vue, Nuxt, Next и Svelte не создаются на первом этапе. Документация остаётся единой и framework-agnostic.

Framework-specific notes допустимы только как примечания, examples или future extensions, если они не размывают каноническую FEOD.

#### Rationale

- PRD требует не делать FEOD зависимым от конкретного фреймворка.
- Отдельные framework editions преждевременно превращают одну методологию в набор параллельных доков.
- На первом этапе важнее зафиксировать invariant rules, а не ветвить под экосистемы.

#### Downstream impact

- **Terminology:** не вводить "React FEOD", "Vue FEOD" и аналогичные брендинговые подварианты как нормативные сущности.
- **IA:** основная навигация не дробится по фреймворкам.
- **Tools:** инструменты описываются на уровне методологии; framework-specific integrations могут быть отдельными примечаниями или будущими материалами.
- **About:** FEOD объясняется как совместимый с несколькими frontend-стеками без создания отдельных редакций документации.

## Что явно вне области первого этапа

Следующие темы считаются сознательно отложенными, а не нерешёнными:

- отдельная английская версия документации;
- отдельные framework-specific documentation editions;
- каталог нескольких канонических вариаций FEOD;
- техническая реализация Tools;
- VitePress-specific implementation decisions.

## Правила для следующих авторских задач

- В терминологии и структурах использовать только `global`.
- Писать одну нормативную линию FEOD без альтернативных канонов.
- В Tools не обещать зрелый продукт без подтверждённого текущего артефакта.
- В About и introductory-материалах позиционировать FEOD как framework-agnostic методологию для frontend-приложений.
- Не планировать обязательную англоязычную или framework-specific ветку в первом этапе.

## Краткая матрица решений

| Вопрос | Решение |
| --- | --- |
| `global` или `globals` | Канонически только `global`; `globals` допустим лишь как legacy/migration context |
| Одна версия или несколько | Одна каноническая версия FEOD на первом этапе |
| Какие Tools сейчас | Документируем только направления ESLint plugin, AI rules, FEOD config; остальное roadmap или вне области первого этапа |
| FEOD только для frontend? | Да, для frontend-приложений; не привязан к конкретному фреймворку |
| Нужен ли English first | Нет, не в первом этапе |
| Нужны ли отдельные версии под фреймворки | Нет, не в первом этапе |
